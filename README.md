# Language Count

A premium, README-first GitHub language card built as a single Vercel serverless function.

Language Count is designed for developers who want a sharper alternative to generic profile widgets: one endpoint, one focused output, predictable parameters, strict SVG layout discipline, and graceful fallback states that still render as images.

[Português (Brasil)](./README.pt-BR.md)

## Overview

Language Count generates a dynamic SVG card that summarizes the language distribution of a GitHub profile by aggregating repository language byte counts from the GitHub API.

It is intentionally narrow in scope:

- one public endpoint
- one visual card
- one data model based on GitHub language bytes
- one output format optimized for README embeds and portfolio pages

The project is visually inspired by the old `github-readme-stats` top-languages card, but it takes a more opinionated approach to presentation, layout consistency, and error-state quality.

## Why This Card Exists

Most language cards solve the data problem and stop there. Language Count also treats the SVG itself as a product surface.

Key goals:

- produce a polished card that feels deliberate instead of autogenerated
- stay reliable inside GitHub README rendering constraints
- preserve visual quality across small and medium widths
- avoid overflow, clipping, and loose alignment
- keep the public interface small enough to remain stable

## Query Parameters

| Parameter            | Type                   | Default | Range / Format            | Description                                                    |
| -------------------- | ---------------------- | ------- | ------------------------- | -------------------------------------------------------------- |
| `username`           | string                 | none    | GitHub username           | Profile to analyze. Required.                                  |
| `hide`               | comma-separated string | none    | `html,css,shell`          | Additional languages to exclude. Matching is case-insensitive. |
| `langs_count`        | integer                | `6`     | `1-20`                    | Maximum number of languages rendered on the card.              |
| `card_width`         | integer                | `360`   | `280-560`                 | Card width in SVG pixels. Height is computed automatically.    |
| `disable_animations` | boolean                | `false` | `true`, `false`, `1`, `0` | Disables row and bar entrance animations when enabled.         |

## How It Works Internally

Language Count follows a simple but deliberate request pipeline.

1. Parse and normalize query parameters.
2. Build the hidden-language filter set.
3. Fetch the target user’s repositories from the GitHub REST API.
4. Ignore forked repositories.
5. Fetch `languages_url` for each remaining repository in parallel.
6. Aggregate byte counts per language.
7. Drop hidden languages.
8. Compute percentages from total byte volume.
9. Sort languages descending by byte count.
10. Render a width-aware SVG card.

## Serverless Function Architecture

The project is intentionally compact:

```text
.
├─ api/
│  └─ index.mjs
├─ fonts/
│  └─ Azonix.otf
├─ package.json
├─ vercel.json
├─ README.md
└─ README.pt-BR.md
```

### Runtime model

- The entire public surface is routed to `api/index.mjs`.
- `vercel.json` maps every incoming route to the same serverless function.
- The function is configured with `maxDuration: 10`.
- There is no persistent storage layer.
- There is no build step for the SVG itself.
- The SVG font is embedded from `fonts/Azonix.otf` at runtime.

## GitHub API Collection Pipeline

The current implementation uses:

- `GET /users/{username}/repos?per_page=100&type=owner`
- each repository’s `languages_url`

Important behavior:

- only owner repositories are considered
- forked repositories are ignored
- the request currently reads the first page only
- the data model is based on GitHub’s language byte counts

That means the card should be read as **public repository byte distribution**, not as a full skill or experience model.

## Filter System

The filter pipeline combines two layers:

### Built-in hidden languages

By default, the project suppresses presentation-heavy or infrastructure-heavy languages such as:

- HTML
- CSS
- SCSS
- Less
- Blade
- Dockerfile
- Shell
- Batchfile
- PowerShell
- Makefile

### User-provided hide list

The `hide` query parameter extends that default set.

Example:

```text
?username=Joaopdiasventura&hide=markdown,json
```

Filter matching is case-insensitive.

## SVG Rendering Model

The card renderer is not a static template. It computes layout values from width and language count.

Rendered elements include:

- card shell and border system
- header block
- divider line
- row grid
- language dots
- aligned labels
- tabular percentages
- bounded progress bars
- empty and error-state panels

The renderer also clips decorative content to the card shape to prevent overflow beyond the rounded container.

## Animation System

Language Count uses restrained SMIL animation so the SVG remains self-contained.

Current animation behavior:

- row groups fade in with a slight stagger
- progress bars expand from zero width
- animations run once
- no infinite loops
- `disable_animations=true` emits the final static state

## Cache Strategy

The endpoint returns:

```text
Cache-Control: s-maxage=3600, stale-while-revalidate=86400
```

This means:

- Vercel may cache the generated result for up to 1 hour
- stale content may continue to be served while a fresh version is regenerated
- repeat requests are cheaper than rebuilding the SVG on every hit

## Performance Notes

The project is small, but there are still a few intentional performance choices:

- repository language fetches are executed with `Promise.all`
- the SVG is assembled as a string with no browser runtime
- width and height are computed directly with lightweight math helpers
- the response is cacheable
- an optional GitHub token can reduce rate-limit pressure

## Error Handling

The function always aims to return a valid SVG response body, even when the underlying request fails.

| Scenario                           | HTTP status     | Card behavior                          |
| ---------------------------------- | --------------- | -------------------------------------- |
| Missing `username`                 | `400`           | Returns an input-required SVG card     |
| User not found                     | `404`           | Returns a profile-unavailable SVG card |
| GitHub rate limit / upstream issue | upstream status | Returns an unavailable SVG card        |
| Unexpected runtime failure         | `500`           | Returns a generation-error SVG card    |

This is important for image embeds because a broken card is worse than a readable fallback.

## Limitations

- The project currently reads only the first 100 owner repositories.
- Organization repositories are not included unless they are owned directly by the user account queried.
- Forks are intentionally excluded.
- The card does not support custom themes.
- The visual system is currently dark-only.
- The card is based on GitHub language bytes, not lines of code or project importance.
- Even with `GITHUB_TOKEN`, repository enumeration still targets the public `/users/{username}/repos` endpoint.
- There is no automated test suite in the repository.

## Deploying on Vercel

### Option 1: Import the repository

1. Create a new Vercel project from the repository.
2. Add `GITHUB_TOKEN` if you want higher GitHub API resilience.
3. Deploy.

### Option 2: Vercel CLI

```bash
npm install
npx vercel
npx vercel --prod
```

The route configuration in `vercel.json` already maps all requests to `api/index.mjs`.
